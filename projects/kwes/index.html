What KWES is

  • github.com/aykhan019/kwes
  • Python 3.11+
  • Apache-2.0
  • v0.1.0 · pre-1.0

KWES: Kapital Web Exposure Scanner is a configuration-driven orchestrator that runs seven established security CLIs against assets an allowlist explicitly authorizes. It handles scope enforcement, one shared traffic budget, process-group cancellation, secret redaction, raw-evidence preservation and resumable runs, then normalizes every tool's output into a single finding model with evidence attached. It was built for, and named after, the estate it was first written to assess — but nothing in it is specific to that estate. The scope file is the only thing that decides what gets touched.

What it is not

KWES is not a vulnerability-detection engine, and not a substitute for a penetration test. It discovers and reports; a human validates. Every automated result is recorded unverified until a person says otherwise, and the severity a tool claimed (severity_raw) is kept in a separate field from the severity an analyst assigns. Conflating those two is what makes automated security reports untrustworthy.

The rest of this page is ordered so a reader can stop at any point and have gotten something: the legal constraint first, then what the seven stages do and how each one is wrong, then the controls that make it defensible, then how to run it.

Authorized use only

Read this before installing

KWES sends real traffic to real systems. Scanning infrastructure you do not own or have written authorization to test is unlawful in most jurisdictions — including the Computer Misuse Act (UK), the Computer Fraud and Abuse Act (US), and equivalents elsewhere. Authorization is the user's responsibility, not the tool's.

KWES is designed so that the safe path is the only path, but no tool can verify that your paperwork is real. Three things follow from that:

  • There is no --target flag. Scope is a file containing an authorization block that names who approved the work, under what reference, and until when. Without it the run does not start.
  • Discovery never grants permission. A hostname from subfinder, a CNAME from dnsx, or a URL from a crawler is inventory. It is re-checked against your allowlist at the adapter boundary before any stage can touch it — not once at startup, because every stage generates new targets that nobody authorized.
  • CDN-fronted assets are refused even when the hostname is in your allowlist. You cannot authorize testing of infrastructure you do not own, and neither can the organization that hired you.

If you are running KWES against an estate you do not personally own, keep the signed authorization for as long as you keep the run directory. manifest.json records the scope, the authorization block, the tool versions, and the rate limit in force — "how fast did you scan us" is the first question after any complaint, and the answer needs to come from the run record.

The pipeline

subfinder → dnsx → httpx → katana → jsluice → ffuf → nuclei → normalization

Seven stages. The "How it is wrong" column is not a disclaimer bolted on at the end — it is the reason a human validates everything KWES reports, and it is the most useful thing on this page.

# Stage Tool What it adds How it is wrong
1 subdomains subfinder Hostnames under a root domain, from certificate transparency and passive DNS. Sends nothing to the target. Returns dead hostnames and names owned by other people.
2 dns dnsx A/AAAA/CNAME records, plus wildcard-DNS detection. A wildcard record makes every invented name look alive; without the probe one record inflates the inventory by hundreds.
3 http httpx Which hosts actually answer, with status, title, server, TLS, and technology guesses. Technology detection is a header-and-body guess. It routes later checks; it never proves a version.
4 crawl katana The routes behind each live URL — pages, API paths, form parameters. Reports links it found, including 404s and routes retired years ago.
5 js_analysis jsluice API paths parsed out of JavaScript bundles, which no page links to. Every high-entropy string looks like a key; build hashes dominate the noise.
6 content_discovery ffuf Paths nobody advertised — the forgotten admin panel, the exposed .git. Soft-404s above all. A site answering 200 for missing pages makes every guess a hit.
7 findings nuclei Template matches for known exposures and misconfigurations. A template match is a pattern match, not a proof.

Terms used above

  • CNAME — a DNS record making one hostname an alias for another. When www.example.com is a CNAME for example.map.fastly.net, the domain's own owner is stating that Fastly serves it. That is the strongest signal KWES has that a name is fronted by a third party, and it is visible before any HTTP request.
  • Wildcard DNS — a record that answers for every name under a domain, including names nobody created. Without a probe that resolves an invented hostname, one wildcard record makes hundreds of guessed names look like live hosts.
  • Soft-404 — a page answering HTTP 200 with a "not found" body instead of a 404 status. To a content-discovery tool every wrong guess then looks like a hit, so a 500-word list "finds" 500 paths that do not exist. ffuf's per-host auto-calibration is what filters those.
  • Template match — a Nuclei template describes a request and a pattern its response should contain. A match means the pattern was present, not that the issue is exploitable.

Order lives in configuration, not in code

The order lives in config/pipeline.yaml. No module encodes "after httpx comes katana" — stages connect by declared input/output kind, so any stage can be disabled or reordered without touching Python. A stage whose input and output kinds match is a verification step that narrows the working set, which is how the DNS stage removes hostnames that turned out not to resolve.

Stage 6 is the only one that needs a capability grant. Guessing at unadvertised paths is more intrusive than following links, so ffuf declares requires_capabilities = {directory_fuzzing} and the orchestrator refuses the stage unless both the profile and the scope document grant it. The shipped safe and fast profiles leave it off.

The safety model

These are enforced in code, by types and tests, rather than by documentation and reviewer discipline. tests/unit/test_architecture.py fails the build if an adapter imports the pipeline, or if a module outside the runner spawns a process.

Scope is a type, not a check

Adapters accept only AuthorizedTarget values, and ScopePolicy.authorize() alone can construct one — the constructor demands a sentinel object that only kwes/scope/policy.py holds. Passing a raw string is a type error caught by mypy, not a review miss. A single upfront check would run before the risky data exists; every stage generates new targets, so the gate sits immediately before traffic is sent.

Refusals are recorded rather than silently dropped, each with a structured reason: not_in_allowlist, explicitly_excluded, cdn_fronted, wildcard_artifact, or malformed. An operator who cannot see what was skipped has no way to tell a correct scope file from a broken one — a typo that excludes everything looks exactly like a clean scan.

One traffic budget, not one per tool

Five tools each capped at 50 requests/second is 250 requests/second arriving at the target. Every tool derives its rate flag from one configured number, and no two active stages run against the same host concurrently. httpx and nuclei both default to 150 on their own, which is why KWES always passes the flag explicitly.

The shipped default is 10, not 50

config/tools.yaml ships target_rate_limit: 10, and it defaults low on purpose. 10 is the rate you can run against an estate before you know which host is a marketing page and which is a payment gateway — nothing in KWES can tell those apart, so the default assumes the worst one. The 50 above is the illustration of why per-tool limits do not compose, not the setting.

No stated rate limit is not permission to scan fast. Web application firewalls commonly rate-limit a single source address somewhere in the 50–100 range; tripping one blocks your address and ends the run — a self-inflicted outage, plus an alert somebody has to explain. A critical-only sweep is roughly 1,560 requests per live URL, so 500 URLs is about 21.7 hours at 10/s and 4.3 at 50/s. If your window does not fit, split the scope into batches rather than raising the rate — two runs at a reviewed rate are safe; one run at double the rate is not.

One subprocess site

tools/runner.py is the only place a process is spawned. It is the single place that enforces timeouts, process-group cancellation, and the no-shell rule — a second spawn site would silently opt out of all three, and a test asserts no other module can spawn.

No shell=True, ever, and no command strings built by interpolation. Argument lists only. A hostname is attacker-influenced input — it arrives from a certificate transparency log or a passive DNS API — and the difference between passing an argv list and using a shell is the difference between a hostname and command execution on your own scanning host. Hostnames are additionally shape-checked, which blocks separator injection: the single string evil.net,www.example.com genuinely ends with .example.com, and without that check it would be split back into two names by the tool receiving it.

Cancellation kills the process group. Tools launch in a new session, and Ctrl-C sets a cancellation flag rather than killing Python directly. Signalling only the direct child would leave the tool's own children sending traffic after you believe the run stopped.

Secrets are redacted at ingestion

Redaction happens before anything is written to disk — including before raw tool output is persisted, so there is no window in which an unredacted authorization header, cookie, or token exists in a file. A discovered credential is never tested: when jsluice reports a credential-shaped string in a JavaScript bundle, KWES records that such a string exists and never records its value. Using one is unauthorized access whatever the intent.

Third-party infrastructure is refused

A CDN sits in front of a website: visitors connect to the provider's servers and the provider fetches content from the customer's real server behind the scenes. That creates two distinct problems. Authorization — a request to a Cloudflare edge reaches a machine Cloudflare owns, and the target has no standing to authorize testing it. Attribution — Server: cloudflare says nothing about what the target runs, and a missing security header may be the CDN's configuration rather than the application's.

So CDN-fronted assets are tagged during DNS and HTTP inventory, excluded from active stages, and findings tied to a CDN's IP address are suppressed rather than merely labelled. Detection uses three independent signals: the CNAME chain, the resolved address matched against config/cdn-ranges.yaml (the most common Cloudflare arrangement has no CNAME at all, so the address is the only evidence), and httpx's own detection as a third opinion. None is complete — the exclusions in your scope file remain the authoritative answer.

Resolution is not authorization either: an address is in scope only when the scope file says so. Bank hostnames routinely resolve into CDN and cloud ranges owned by other companies, and shared hosting puts unrelated customers behind one address.

Findings stay unverified

Every finding is recorded unverified. severity_raw holds whatever the tool claimed and stays separate from the severity an analyst assigns, which is empty until a person fills it in. KWES finds candidates, not vulnerabilities.

Skipping work is never skipping scope

--incremental may leave a host out of a stage, but only a stage whose adapter declares itself skippable, only after the host passed scope.authorize() like any other, and only if the manifest and summary name it with the date it is relying on. The incremental/ layer can only remove hosts from a list scope already approved — it has no route to add one. Every uncertainty resolves to scan: an unnecessary scan costs requests, while a wrongly skipped host costs a finding nothing in the report reveals.

Quick start

KWES never installs anything on your behalf. The seven scanners are operator-installed prerequisites. If one is missing, KWES names the binary and fails the run — it will not silently skip a stage or substitute a different tool.

1. The Python package

install
git clone https://github.com/aykhan019/kwes.git
cd kwes
uv tool install --editable .

That puts a kwes command on your PATH, so every example on this page works from any directory — kwes scan ... rather than uv run kwes scan .... --editable means the command tracks this checkout, so a git pull updates the installed tool and the bundled configuration together.

If kwes: command not found, uv installed it to ~/.local/bin, which is not on your PATH: 

uv tool update-shell     # then restart your shell

To develop rather than use, uv sync is enough and uv run kwes ... works without installing anything globally.

2. The scanners

ProjectDiscovery tools, plus ffuf and jsluice:

prerequisites
go install github.com/projectdiscovery/subfinder/v2/cmd/subfinder@latest
go install github.com/projectdiscovery/dnsx/cmd/dnsx@latest
go install github.com/projectdiscovery/httpx/cmd/httpx@latest
go install github.com/projectdiscovery/katana/cmd/katana@latest
go install github.com/projectdiscovery/nuclei/v3/cmd/nuclei@latest
go install github.com/ffuf/ffuf/v2@latest
go install github.com/BishopFox/jsluice/cmd/jsluice@latest

3. The Nuclei template set

Also not vendored, for the same reason:

nuclei -update-templates

4. Confirm the environment

kwes doctor

doctor runs each binary's version flag — a local call that sends no network traffic — and checks the template set is present. Running it first means you find out nuclei is missing before three stages have already sent traffic. Every tool's version output is recorded into each run's manifest, because Go-based tools drift between installs and results are not reproducible without knowing which build produced them.

5. Your first run

quick start
# 1. Write your authorization document.
cp targets/scope.example.yaml targets/scope.yaml
$EDITOR targets/scope.yaml

# 2. Check it loads and see exactly what it would permit. Sends nothing.
kwes validate --scope targets/scope.yaml

# 3. Print the exact command every stage would run. Still sends nothing.
kwes scan --scope targets/scope.yaml --dry-run

# 4. Run it.
kwes scan --scope targets/scope.yaml --profile safe --verbose
Steps 2 and 3 send no packets

validate and --dry-run are the two commands worth building a habit around. Between them they answer "would this start, and what exactly would it be allowed to do" without a single packet leaving the machine.

The scope file

This is the authorization document expressed as configuration, and it is the only thing that grants KWES permission to send traffic anywhere. targets/scope.example.yaml is heavily annotated.

targets/scope.yaml
authorization:
  authorized_by: "Name, Title, Organization"
  reference: "Engagement or ticket reference"
  valid_until: "2026-12-31"

root_domains:        # domains to ENUMERATE UNDER (subfinder is handed these)
  - example.com

subdomains:          # specific approved hosts; nothing is enumerated under them
  - www.example.com

include_subdomains: false   # false: only names written here are in scope

exclusions:          # never touched, even if discovery finds them
  - legacy.example.com

Two things decide how much traffic a run produces:

  • root_domains vs subdomains answer different questions. A root domain is enumerated under. A subdomain is a single approved host. Putting www.example.com in root_domains asks subfinder to find subdomains of that host, which returns nothing and spends minutes doing so.
  • include_subdomains decides whether discovery can widen the run. With true, anything under an approved root is in scope — so a host nobody reviewed becomes a target the moment a certificate transparency log mentions it. false is the right setting for most engagements. What it costs, stated plainly: no wildcard-DNS probe can be sent, because every probe name is invented and no entry authorizes an invented name. Hosts are then reported as unproven for wildcard DNS rather than as proven free of one, and the run names which hosts those are.

exclusions win over everything, from every entry point — including a domain that also appears in root_domains. This is the emergency brake: when someone says "stop testing that host" mid engagement, it goes here and takes effect on the next run. A "*.vendor.example.com" entry excludes every host under the name and the name itself.

An empty key is a deliberate load error. subdomains: with nothing after it is null in YAML, not an empty list, and "deliberately none" and "not filled in yet" are different statements. Write subdomains: [] for the first. KWES refuses to guess.

A separate capabilities block answers "what may be done to these hosts", as distinct from "which hosts". All five — port_scan, directory_fuzzing, authenticated_scanning, source_repository_scanning, dns_brute_force — default to false, and the run uses the intersection of these and the profile's, so neither can widen the other.

Real scope files are authorization documents, not source code. targets/ is gitignored except for the example.

Profiles

A profile is scanning policy: which severities may run, which capabilities are permitted, and how the crawl and fuzzing stages behave. Selected with --profile; the shipped files live in config/profiles/.

safe (default) fast deep
For Conservative default Estate-wide triage Short vetted host list
Severities low → critical high, critical info → critical
Content discovery off off on
Crawl — — depth 3, 10 min/host
Relative cost baseline ~4× faster ~4× slower

All three exclude the intrusive, dos, brute-force, fuzzing, headless, and code template tags, and all three run HTTP templates only.

A host that passes fast has not been fully checked — it has been checked for high-and-critical findings only. The summary says so. The intended shape is two passes: fast across the estate to find the serious and obvious problems, then deep against a short scope file of the hosts that came back interesting plus the ones you already know matter — login portals, admin interfaces, anything handling money or customer data.

--config-dir <path>
Directory holding pipeline.yaml, tools.yaml, and profiles/. Default: the config/ directory of the KWES checkout the command was installed from. Accepted by validate, doctor, and scan. Profile name under config/profiles/. Default: safe. Shipped values: safe, fast, deep. Accepted by validate, doctor, and scan. --scope <path> · required
Path to the scope file authorizing this run. --severity <list>
Comma-separated severities to run templates for, drawn from info,low,medium,high,critical. Default: unset — the profile's own list applies. Accepted by validate and scan. This is the single biggest lever on runtime: critical alone is roughly a quarter of the time of low-and-above. It narrows a profile and cannot widen one. A severity set sharing nothing with the profile is refused rather than honoured, and the narrowing is recorded in the manifest so a report states the severities that actually ran rather than the ones the profile permits.

Raising is a deliberate edit to config/tools.yaml, because that file is what the run manifest records and what the authorization rests on. Lowering pulls concurrency down with it — leaving 25 sockets open while sending 5 requests a second is a connection flood with a slow request rate, which is what a target's monitoring actually notices.

kwes validate

kwes validate --scope <path> [--profile <name>] [--config-dir <path>] [--severity <list>] [--rate <n>]

Purpose: load and check all configuration without running anything. It answers "would this start, and what exactly would it be allowed to do" without sending a single packet.

Required: --scope. Optional: --profile (default safe), --config-dir, --severity, --rate — all as described above. Network traffic: none.

Configuration interactions: it loads pipeline.yaml, tools.yaml, the named profile, the template-routing and CDN range tables, and your scope file; checks every stage name against the adapter registry, so a typo in pipeline.yaml fails here rather than after earlier stages have sent traffic; then runs the same traffic-budget check scan runs, refusing a configuration whose stages would together exceed target_rate_limit.

Output: configuration is valid followed by the resolved profile, the enabled stage order, the target and discovery rate limits with the tools drawing on each, concurrency, the severities that would run, allowlist sizes, and the granted capabilities — shown as the intersection of profile and scope.

Exit: 0 when valid. 1 on a configuration error, a traffic-budget violation, a --rate above the budget or not positive, or a --severity set that shares nothing with the profile.

Minimal

kwes validate --scope targets/scope.yaml

Realistic

Confirming that tonight's gentler, critical-only pass over a fragile batch would start — and printing what it would be allowed to do — before committing to it: 

kwes validate --scope targets/payments-batch.yaml \
              --profile fast --severity critical --rate 5

kwes doctor

kwes doctor [--config-dir <path>] [--profile <name>]

Purpose: check that every tool an enabled stage needs is actually installed. Separate from validate, which only reads files: this runs each tool with its version flag and checks nuclei's template set is present.

Required: none. Optional: --config-dir, --profile (default safe). Notably it takes no --scope — your environment is the same whatever you are authorized to scan. Network traffic: none. Each binary is invoked locally with its version flag.

Configuration interactions: which tools are checked follows from which stages pipeline.yaml enables and which binary names tools.yaml gives them, so disabling a stage stops doctor demanding its tool. It cannot install anything — KWES does not install tools or download templates, because that would change your environment and make the run depend on whichever version happened to be current today.

Output: one line per enabled stage — ok with the reported version, or MISSING with the binary name that is not on PATH. The nuclei entry additionally prints its resolved templates directory. Ends with all required tools are present, or a count of problems.

Exit: 0 when everything is present. 1 when any binary is missing, when the nuclei template set is missing, or when configuration fails to load.

Minimal

kwes doctor

Realistic

A scheduled pre-flight on a machine only ever used for estate-wide sweeps, checked against the exact profile those sweeps use: 

kwes doctor --profile fast

kwes scan

kwes scan --scope <path> [--profile <name>] [--config-dir <path>] [--runs-dir <path>] [--dry-run] [--verbose | -v] [--resume <run_id>] [--severity <list>] [--rate <n>] [--incremental]

Purpose: run the configured pipeline against an authorized scope. Order comes from config/pipeline.yaml, not from the CLI, and every target a tool discovers is re-checked against the scope file before the next stage can touch it.

Required: --scope. Network traffic: yes — this is the command that sends it — unless --dry-run is given.

Options specific to scan

--runs-dir <path>
Where run directories are created. Default: runs/ in the KWES checkout. Also where incremental-state.json is looked for. It changes where evidence is written, not what is collected.
--dry-run
Default: off. Print the exact argv each stage would run, plus the contents of the target list files, and send nothing. The preview is deliberately built without an incremental effort policy, so it shows the widest thing the pipeline could send — a preview narrowed by last night's state would understate the commands, and an operator reads a preview and believes it. Stages whose real input only exists once earlier stages have run are labelled as showing placeholders. It cannot create a run directory or produce findings.
--verbose, -v
Default: off. Adds detail to the live trace: the target names themselves, a per-second heartbeat with observed throughput, which invocation is running, and a running total. The stage-by-stage trace is always shown regardless. It deliberately cannot show a percentage or an estimated finish time — none of the orchestrated tools reports how much work remains, so any completion figure would be a guess printed as a fact.
--resume <run_id>
Default: unset — a new run id is generated. Continue an existing run id, replaying stages already marked done from their preserved raw output. Parsing and normalization are pure functions of that output, so the same state is rebuilt and no traffic is sent for those stages.
--incremental
Default: off. Give the full check set only to hosts that need it: those whose fingerprint changed, whose last scan did not finish or did not cover this run's severities, those the check corpus has moved on from, and any host past the configured age limit. Every skipped host is named in the manifest and the summary with the date it is relying on. Requires config/incremental.yaml; without that file the flag is refused rather than defaulted, because the maximum age is the worst-case window in which a newly vulnerable host goes unchecked, and that number has to be one somebody chose and reviewed. It can only remove hosts from a list scope already approved — it has no route to add one, and every uncertainty (unreadable state, a missing fingerprint, an unmeasurable check corpus) resolves to scan.

Output: the run directory path, then a live per-stage trace, then a summary — per-stage status and record counts, host / endpoint / finding totals (findings: N (all unverified)), refused targets broken down by reason rather than totalled, any findings withheld on third-party addresses, elapsed time, the measured check-corpus digest, and any hosts an effort policy held back. Files land under runs/<run_id>/, and reports/summary.md is written at the end.

Exit: 0 on a clean run. 1 if any stage finished failed — a partial result is not a clean one, so a scheduled run cannot report success while a tool silently did not run. Also 1 on the configuration, budget, --rate, --severity, and missing-incremental.yaml errors described above. Ctrl-C (SIGINT) and SIGTERM do not kill the process directly: they set a cancellation flag, and the runner terminates the running tool's whole process group.

Minimal

kwes scan --scope targets/scope.yaml

Realistic

The first of the two passes — an estate-wide triage sweep, narrowed to critical templates to fit the window, with the live trace on because it will run for hours: 

kwes scan --scope targets/scope.yaml \
          --profile fast --severity critical --verbose

And picking that run back up after it was interrupted:

kwes scan --scope targets/scope.yaml --resume 20260727T204420Z-f904

Output contract

Each run writes to runs/<run_id>/:

runs/<run_id>/
runs/<run_id>/
├── raw/<tool>/                   # original tool output, unmodified except redaction
├── normalized/
│   ├── assets.jsonl              # hosts, and what each stage learned
│   ├── endpoints.jsonl           # URLs and API routes
│   └── findings.jsonl            # normalized findings
├── reports/summary.md            # coverage, counts, affected assets
└── manifest.json                 # scope, authorization, tool versions,
                                  # per-stage status, refused targets

Why raw output is preserved

Normalization is lossy, and a finding without its source evidence cannot be validated — which makes it worthless in a report. Given that every stage produces false positives in a documented way, the evidence is not an archival nicety: it is the only thing that lets an analyst turn a candidate into a confirmed finding, or dismiss it. Raw output is redacted before it is written, so preserving it does not mean preserving secrets.

Crash safety and resume

Records are appended as they arrive, so a crash in a later stage never destroys earlier results. assets.jsonl is an append log during the run and is collapsed to one record per host, atomically, at the end; if the run dies first the uncollapsed log survives, which loses nothing.

manifest.json is the resume point. Parsing and normalization are pure functions of preserved raw output, so kwes scan --resume <run_id> rebuilds the same state and sends no traffic for stages already marked done.

runs/incremental-state.json sits beside run directories because it describes what is true across runs. It is derived, never authoritative: it records what happened and grants nothing. Deleting it is always safe and costs one full scan.

runs/ is gitignored. It contains findings, raw output, and evidence from real infrastructure — treat a run directory with the same care as the report you write from it.
